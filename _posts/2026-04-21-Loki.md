# 모니터링 시스템 구축 및 Loki 이중화 정리

## 1. 문서 목적

이 문서는 **모니터링 시스템 구축**, **Loki General / Loki Critical 이중화**, **S3 연동**, **Grafana 조회 구조**, **Fluent Bit 라우팅**, **운영 중 겪었던 트러블슈팅**을 한 번에 정리한 문서다.

특히 아래 내용을 중심으로 정리한다.

- Docker Compose 기반 모니터링 스택 구성
- Spring Boot 로그를 Fluent Bit로 수집하는 구조
- General / Critical 로그 분리 설계
- Loki-General 과 Loki-Critical 의 저장소 차이
- Loki-Critical 의 S3 적재 구조
- Grafana 에서 오래된 로그를 조회하는 원리
- 실제 운영 중 발생한 문제와 해결 과정
- 테스트용 API, 확인용 명령어, 배포/재기동/검증 절차

---

## 2. 전체 아키텍처 개요

현재 구성의 핵심 흐름은 아래와 같다.

```
Spring Boot App
  -> Docker logging driver (fluentd)
    -> Fluent Bit (forward input)
      -> Loki-General
      -> Loki-Critical
        -> S3 (faithb-loki-critical)

Grafana
  -> Loki-General 조회
  -> Loki-Critical 조회
```

### 현재 역할 분리

- **Spring Boot App**
    - JSON 형식 로그를 stdout/stderr 로 출력
- **Docker logging driver = fluentd**
    - 컨테이너 로그를 Fluent Bit 로 전달
- **Fluent Bit**
    - 로그 파싱
    - 조건에 따라 General / Critical 로 분기
- **Loki-General**
    - 일반 로그 저장소
    - 로컬 filesystem + Docker named volume 사용
- **Loki-Critical**
    - 중요 로그 저장소
    - S3 object store 사용
- **Grafana**
    - Loki datasource 를 통해 로그 조회
    - S3 를 직접 읽지 않음

## 4. Git 반영 및 운영 폴더 동기화 구조

운영 구조는 아래처럼 분리되어 있었다.

- `~/upload-repo` : Git pull 받는 저장소
- `~/monitoring-test` : 실제 운영 폴더

즉 변경사항 반영 절차는 아래와 같다.

1. `upload-repo` 에서 `git pull`
2. `monitoring-test` 컨테이너 종료
3. `upload-repo/monitoring-test` -> `~/monitoring-test` 동기화
4. 다시 `docker compose up -d --build`

### 추천 동기화 방식

`cp` 보다는 `rsync` 권장.

```bash
cd ~/upload-repo
git pull origin main

cd ~/monitoring-test
docker compose down --remove-orphans

cd ~
cp -r monitoring-test monitoring-test.backup.$(date +%Y%m%d_%H%M%S)

rsync -av --delete ~/upload-repo/monitoring-test/ ~/monitoring-test/

cd ~/monitoring-test
docker compose up -d --build
```

### 주의

- `-delete` 옵션은 운영 폴더에만 있는 파일도 삭제한다.

예: `.env`, `logs/`, `data/`, 키파일 등

필요 시 제외:

```bash
rsync -av --delete \
  --exclude='.env' \
  --exclude='logs/' \
  --exclude='data/' \
  ~/upload-repo/monitoring-test/ ~/monitoring-test/
```

## 5. Docker / Compose 관련 개념 정리

### 5.1 `docker compose down` 의 의미

- 현재 프로젝트의 컨테이너/네트워크/리소스를 내림
- `-remove-orphans` 옵션을 사용하면 현재 compose 파일에 없는 고아 컨테이너도 정리 가능

```bash
cd ~/monitoring-test
docker compose down --remove-orphans
```

### 5.2 컨테이너가 안 내려가는 경우

실제로 `monitoring-test-app-1` 이 `Stopping` 상태에서 오래 멈춘 적이 있었다.

가능한 원인:

- Java/Spring Boot 프로세스가 graceful shutdown 중 hang
- PID 1 신호 처리 문제
- Docker daemon 이 해당 컨테이너 정리를 끝내지 못하는 상태
- 파일시스템 / I/O 대기 문제

### 우선 시도할 명령어

```bash
docker compose down --remove-orphans --timeout 5
```

### 개별 컨테이너 강제 종료

```bash
docker kill monitoring-test-app-1
docker rm -f monitoring-test-app-1
```

### 그래도 hang 이면

```bash
sudo systemctl restart docker
```

상황에 따라 `docker kill` 자체가 hang 될 수 있다. 그 경우는 컨테이너 하나가 아니라 **Docker daemon/containerd 정리 문제**일 가능성이 높다.

### 확인용 명령어

```bash
docker ps -a
docker inspect monitoring-test-app-1 --format '{{.State.Status}} {{.State.Pid}} {{.State.Running}}'
sudo systemctl status docker --no-pager
sudo systemctl status containerd --no-pager
```

## 7. Docker logging driver 와 Fluent Bit 관계

Compose 설정에서 Spring Boot 컨테이너의 logging driver 를 `fluentd` 로 두면, 앱이 stdout/stderr 로 출력한 로그를 Docker 가 Fluent Bit 로 넘긴다.

핵심은:

- **Spring Boot 가 Fluent Bit 에 직접 전송하는 것이 아님**
- **Docker 엔진이 로그를 받아 Fluent Bit 로 전달**

흐름:

```
Spring Boot stdout/stderr
  -> Docker logging driver: fluentd
    -> fluent-bit:24224
```

따라서 `fluent-bit` 서비스가 죽어 있으면 라우팅 테스트 자체가 제대로 되지 않는다.

## 8. Fluent Bit 구성과 라우팅 로직

### 8.1 최종 의도

- 일반 로그는 `loki-general` 로 보냄
- WARN / ERROR / `결제실패` 메시지는 `loki-critical` 로 보냄

### 실제 확인된 라우팅 규칙

```
[FILTER]
    Name              parser
    Match             spring-app
    Key_Name          log
    Parser            spring_json
    Reserve_Data      On
    Preserve_Key      Off

[FILTER]
    Name              rewrite_tag
    Match             spring-app
    Rule              $level ^(ERROR|WARN)$ track.critical false
    Rule              $message .*결제실패.* track.critical false
    Emitter_Name      crit_emitter

[OUTPUT]
    Name              loki
    Match             track.critical
    Host              loki-critical
    Port              3100
    Labels            job=spring-app,track=critical

[OUTPUT]
    Name              loki
    Match             spring-app
    Host              loki-general
    Port              3100
    Labels            job=spring-app,track=general
```

### 의미

- 원본 태그는 `spring-app`
- `rewrite_tag` 필터가 조건을 만족하면 `track.critical` 태그를 새로 부여
- `false` 이므로 원본은 유지하지 않고 critical 로만 보냄

즉 **완전 분리** 구조다.

### 실제 분기 결과

| 조건 | 결과 |
| --- | --- |
| INFO 일반 로그 | General |
| WARN | Critical |
| ERROR | Critical |
| 메시지에 `결제실패` 포함 | Critical |

즉 `payment-failure` 는 INFO 레벨이라도 메시지 기준으로 Critical 이 된다.

## 9. Fluent Bit 기동 실패 이슈와 해결

### 9.1 실제 증상

`fluent-bit-1 exited with code 1`

로그:

```
Sections 'multiline_parser' and 'parser' are not valid in the main configuration file.
It belongs to the 'parsers_file' configuration files.
[error] configuration file contains errors, aborting.
```

### 원인

`[PARSER]` 또는 `[MULTILINE_PARSER]` 블록을 **메인 `fluent-bit.conf` 안에 넣었기 때문**이다.

즉 다음과 같은 구성이 잘못된 상태였다.

```
[SERVICE]
    Flush         1
    Log_Level     info

[PARSER]
    Name        spring_json
    Format      json
```

### 올바른 방식

- `fluent-bit.conf` 에는 `SERVICE`, `INPUT`, `FILTER`, `OUTPUT` 위주만 둔다.
- parser 정의는 별도 `parsers.conf` 에 둔다.
- `Parsers_File parsers.conf` 로 연결한다.

### 수정 예시

### `fluent-bit/parsers.conf`

```
[PARSER]
    Name        spring_json
    Format      json
```

### `fluent-bit/fluent-bit.conf`

```
[SERVICE]
    Flush         1
    Log_Level     info
    Parsers_File  parsers.conf

[INPUT]
    Name              forward
    Listen            0.0.0.0
    Port              24224

[FILTER]
    Name              parser
    Match             spring-app
    Key_Name          log
    Parser            spring_json
    Reserve_Data      On
    Preserve_Key      Off

[FILTER]
    Name              rewrite_tag
    Match             spring-app
    Rule              $level ^(ERROR|WARN)$ track.critical false
    Rule              $message .*결제실패.* track.critical false
    Emitter_Name      crit_emitter

[OUTPUT]
    Name              loki
    Match             track.critical
    Host              loki-critical
    Port              3100
    Labels            job=spring-app,track=critical

[OUTPUT]
    Name              loki
    Match             spring-app
    Host              loki-general
    Port              3100
    Labels            job=spring-app,track=general
```

### 수정 후 확인

```bash
cd ~/monitoring-test
docker compose up -d --build

docker compose ps
docker compose logs --tail=100 fluent-bit
```

정상이라면 더 이상 parser 오류가 나오지 않아야 한다.

## 10. Grafana datasource 와 저장 위치의 차이

Grafana 화면에서 확인된 datasource 는 다음과 같았다.

- `Loki-Critical` -> `http://loki-critical:3100`
- `Loki-General` -> `http://loki-general:3100`

### 중요 개념

이 화면은 **Grafana 가 어디에 질의하는지**를 뜻할 뿐이고,
**로그를 어디에 저장하는지**를 의미하지는 않는다.

즉:

- Grafana datasource = 조회 대상 Loki 서버
- 실제 저장 위치 = 각 Loki 의 `loki-*.yaml` 설정

그래서 `Loki-Critical` 이 S3-backed 인지, `Loki-General` 이 local filesystem 인지는 **Grafana 화면이 아니라 Loki 설정 파일**을 봐야 한다.

---

## 11. Loki-General 과 Loki-Critical 의 역할 차이

## 11.1 Loki-General

`loki-general.yaml` 확인 결과:

```
filesystem:
  chunks_directory: /loki/chunks
  rules_directory: /loki/rules

object_store: filesystem
shared_store: filesystem
delete_request_store: filesystem
```

또한 Docker volume 확인 결과:

```
Mountpoint: /var/lib/docker/volumes/monitoring-test_loki_general_data/_data
```

### 결론

`loki-general` 은 **로컬 filesystem 기반 저장**이고, 실제로는 **EC2 호스트의 Docker named volume** 에 저장된다.

즉 단순 컨테이너 레이어가 아니라 다음 경로에 보관된다.

```
/var/lib/docker/volumes/monitoring-test_loki_general_data/_data
```

### 특징

- 컨테이너 재생성 시 volume 이 남아 있으면 데이터 유지 가능
- 하지만 EC2 인스턴스 장애 / volume 삭제 시 손실 가능
- S3 장기보관 아님

---

## 11.2 Loki-Critical

`loki-critical.yaml` 확인 결과:

```
schema_config:
  store: boltdb-shipper
  object_store: s3

storage_config:
  boltdb_shipper:
    shared_store: s3
  aws:
    s3: s3://ap-northeast-2/faithb-loki-critical

compactor:
  shared_store: s3
  delete_request_store: s3
```

### 결론

`loki-critical` 은 **S3-backed Loki** 다.

즉 index/chunk/delete metadata 의 최종 저장소는 S3 버킷 `faithb-loki-critical` 이다.

### 특징

- 중요한 로그의 장기 보관 가능
- EC2 재기동 / 컨테이너 재생성과 무관하게 S3 에 남음
- Grafana 는 직접 S3 를 읽는 것이 아니라 `loki-critical` 을 통해 조회

---

## 12. S3 에 생성된 실제 객체 해석

버킷에서 확인된 예시:

```
2026-04-16 11:01:37        928 fake/b64d985de6b9d02:19d93e537b0:19d93e9db30:e2661040
2026-04-16 12:04:20        135 index/delete_requests/delete_requests.gz
2026-04-16 11:24:26        515 index/index_20559/compactor-1776306265.gz
```

### 각각의 의미

### `fake/...`

- 실제 로그 chunk 후보
- tenant 가 `fake` 로 저장된 형태

### `index/index_20559/compactor-....gz`

- index 파일
- compactor 가 생성한 압축된 인덱스

### `index/delete_requests/delete_requests.gz`

- 로그 본문이 아님
- 삭제 요청 메타데이터 파일

### 정리

| S3 Key 패턴 | 의미 |
| --- | --- |
| `fake/...` | 실제 chunk 데이터 후보 |
| `index/index_*/...` | index |
| `index/delete_requests/...` | 삭제 요청 메타데이터 |

## 13. “S3 에 자동 적재되는가?”에 대한 정리

질문 핵심:

> 분명 `faithb-loki-critical` 버킷을 만들었고 롤도 주입했는데, 왜 로그가 안 보이냐?
> 

### 결론

**예, 설정대로라면 Loki-Critical 로그는 S3 에 적재되는 구조가 맞다.**

다만 다음 차이를 이해해야 한다.

- Grafana 에서 조회된다고 해서 **그 순간 즉시 S3 에 flush 된 것**은 아님
- 아주 최근 로그는 메모리 / active index / cache 단계에 있을 수 있음
- 일정 시간이 지나면 chunk 로 S3 에 내려감

### 실제로 권한이 살아있다는 근거

S3 에 아래 파일들이 생성되었다.

- `index/delete_requests/delete_requests.gz`
- `index/index_20559/compactor-....gz`
- `fake/...`

즉 버킷 write 자체는 되고 있었다.

## 14. 오래된 로그 조회 원리

질문 핵심:

> `loki-critical` 을 선택해서 오래된 로그를 보면, S3 에 있는 로그를 `loki-critical` 이 뒤져서 보여주는 거냐?
> 

### 답

**맞다. 정확히는 아래 구조다.**

```
Grafana
  -> Loki-Critical
     -> S3 index 조회
     -> 필요한 chunk 조회
     -> 결과 반환
```

즉:

- Grafana 가 S3 를 직접 조회하지는 않음
- Grafana 는 Loki datasource 에 질의함
- `loki-critical` 이 S3 의 index/chunk 를 찾아서 결과를 보여줌

### 최근 로그 vs 오래된 로그

### 아주 최근 로그

- 아직 S3 flush 전일 수 있음
- 메모리 / active index / cache 에서 보일 수 있음

### 오래된 로그

- flush 완료된 후 S3 에 존재
- `loki-critical` 이 S3 에서 읽어와서 보여줌

## 15. Grafana 에서 조회하는 방법

### Critical 조회

```
{job="spring-app", track="critical"}
```

세부 메시지 확인:

```
{job="spring-app", track="critical"} |= "데모 WARN 로그"
```

```
{job="spring-app", track="critical"} |= "데모 ERROR 로그"
```

```
{job="spring-app", track="critical"} |= "결제실패"
```

### General 조회

```
{job="spring-app", track="general"}
```

```
{job="spring-app", track="general"} |= "/api/test 엔드포인트가 호출됨"
```

### 시간 범위 주의

과거 S3 기반 로그를 보려면 Explore 에서 시간 범위를 넓혀야 한다.

## 16. `job` 라벨이 안 보였던 이유

질문 당시 Grafana 에서 Select label 에 `job` 이 보이지 않았다.

### 원인 정리

초기에는 두 가지 가능성을 봤다.

1. 라벨을 설정하지 않았을 가능성
2. 실제로 로그가 Loki 로 들어오지 않았을 가능성

그 후 `fluent-bit.conf` 를 확인하니 실제로는 아래처럼 설정되어 있었다.

```
Labels            job=spring-app,track=critical
Labels            job=spring-app,track=general
```

즉 라벨 자체는 붙도록 되어 있었고,
진짜 문제는 **Fluent Bit 가 parser 설정 오류로 죽어 있었다는 점**이었다.

### 결론

- `job` 라벨이 안 보였던 것은 라벨 정의가 없어서가 아니라
- **Fluent Bit 기동 실패로 로그가 정상 인입되지 않았기 때문**이었다.

## 17. Loki 로그에서 보였던 운영 로그 해석

예시:

```
uploading tables
handing over indexes to shipper
syncing tables
query readiness setup completed
```

### 의미

이 로그들은 보통 다음 의미다.

- BoltDB Shipper 가 인덱스 테이블을 업로드 중
- 업로드한 index 를 shipper 에 넘김
- 쿼리용 동기화 수행
- 조회 준비 완료

즉 대체로 **치명 오류라기보다 정상 운영 흐름 로그**에 가깝다.

반대로 아래 같은 내용은 문제 신호였다.

```
Sections 'multiline_parser' and 'parser' are not valid in the main configuration file
configuration file contains errors, aborting
```

이건 Fluent Bit 설정 오류로 인해 직접적인 장애 원인이었다.

## 18. S3 객체를 직접 열어보는 방법

### 18.1 Index 파일 보기

예:

```
https://faithb-loki-critical.s3.ap-northeast-2.amazonaws.com/index/index_20559/compactor-1776306265.gz
```

이 파일은 **로그 본문이 아니라 index** 다.

다운로드:

```bash
aws s3 cp \
  s3://faithb-loki-critical/index/index_20559/compactor-1776306265.gz \
  /tmp/compactor-1776306265.gz
```

압축 해제:

```bash
gzip -dc /tmp/compactor-1776306265.gz > /tmp/compactor-1776306265
```

확인:

```bash
file /tmp/compactor-1776306265.gz
file /tmp/compactor-1776306265
strings /tmp/compactor-1776306265 | head -100
hexdump -C /tmp/compactor-1776306265 | head -50
```

### 18.2 Chunk 후보 보기

예:

```
fake/b64d985de6b9d02:19d93e537b0:19d93e9db30:e2661040
```

다운로드:

```bash
aws s3 cp \
  s3://faithb-loki-critical/fake/b64d985de6b9d02:19d93e537b0:19d93e9db30:e2661040 \
  /tmp/loki-critical-chunk
```

확인:

```bash
file /tmp/loki-critical-chunk
strings /tmp/loki-critical-chunk | head -100
strings /tmp/loki-critical-chunk | grep '결제실패'
strings /tmp/loki-critical-chunk | grep '데모 ERROR 로그'
strings /tmp/loki-critical-chunk | grep '데모 WARN 로그'
```

필요 시:

```bash
hexdump -C /tmp/loki-critical-chunk | head -50
```

### 주의

- chunk 는 사람이 바로 읽기 좋은 plain text 가 아닐 수 있음
- index 와 chunk 를 직접 뒤지는 것보다 **Grafana / Loki 조회가 훨씬 편함**

## 19. S3 에서 index / delete / chunk 구분하는 방법

버킷 구조 확인:

```bash
aws s3 ls s3://faithb-loki-critical --recursive | head -100
```

index 만 보기:

```bash
aws s3 ls s3://faithb-loki-critical/index/ --recursive | head -100
```

delete request 보기:

```bash
aws s3 ls s3://faithb-loki-critical --recursive | grep delete_requests
```

chunk 후보 보기:

```bash
aws s3 ls s3://faithb-loki-critical --recursive \
| grep -v ' index/' \
| grep -v 'delete_requests'
```

정리:

- `index/...` -> index
- `delete_requests` -> 삭제 요청 메타데이터
- 그 외 -> chunk 후보

## 22. 현재 구조의 의미와 운영상 장단점

### 장점

### General / Critical 분리

- 일반 로그와 중요 로그를 목적에 따라 분리 가능
- Critical 로그만 장기 보관 가능

- EC2 장애 / 컨테이너 재생성과 무관하게 보존 가능
- 중요한 로그 추적에 유리

### Grafana 조회 통합

- Grafana 에서 datasource 만 바꾸면 General / Critical 비교 가능

### 단점 / 주의점

### 최근 로그와 장기 로그의 저장 타이밍 차이

- 조회 가능 여부와 S3 flush 완료 시점은 다를 수 있음

### General 은 로컬 의존

- EC2 서버 / Docker volume 이 사라지면 함께 사라질 수 있음

### Fluent Bit 에 장애가 나면 전체 라우팅이 멈춤

- parser 설정 오류 하나로 Critical/General 전체 인입이 끊길 수 있음

## 25. 결론

현재 최종 구조는 아래와 같이 이해하면 된다.

```
[앱 로그 발생]
Spring Boot
  -> Docker logging.driver=fluentd
  -> Fluent Bit
     -> General 로그 -> Loki-General -> 로컬 Docker Volume 저장
     -> Critical 로그 -> Loki-Critical -> S3 저장

[조회]
Grafana
  -> Loki-General datasource
  -> Loki-Critical datasource
```

즉,

- **Loki-General** 은 로컬 저장형
- **Loki-Critical** 은 S3 장기보관형
- **Grafana 는 S3 를 직접 읽지 않고 Loki 를 통해 조회**
- **Critical 의 오래된 로그를 본다는 것은 Loki-Critical 이 S3 의 index/chunk 를 찾아서 보여준다는 뜻**

이번 구성과 트러블슈팅을 통해 최종적으로 아래를 확인했다.

1. Fluent Bit 라우팅 규칙으로 General / Critical 분리가 가능하다.
2. parser 설정 오류가 있으면 Fluent Bit 가 즉시 죽는다.
3. `rewrite_tag ... false` 설정으로 Critical 로그를 완전 분리할 수 있다.
4. Loki-Critical 은 실제로 S3 버킷 `faithb-loki-critical` 에 index/chunk/delete metadata 를 적재한다.
5. Loki-General 은 로컬 Docker volume 에 저장된다.
6. Grafana datasource 는 저장소가 아니라 조회 대상 Loki 서버를 뜻한다.
7. 오래된 로그 조회는 Grafana -> Loki -> S3 순서로 이루어진다.
