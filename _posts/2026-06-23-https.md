## 1. AWS ACM (SSL/TLS 인증서 발급)

가장 먼저 도메인에 자물쇠(암호화)를 채우기 위한 인증서를 발급받았습니다.

* **인증서 종류:** DV (Domain Validation / 도메인 소유권 검증형) 퍼블릭 인증서
* **보호 대상 도메인:** `ncc-scm.com` (기본) 및 `wisentm.ncc-scm.com` (서브도메인)
* **검증 방식:** Route 53에 CNAME 레코드를 추가하여 도메인 소유권 자동 검증 (상태: `Issued`)
* **장점:** AWS 리소스 내에서 평생 무료로 사용 가능하며, 만료 전 자동 갱신됨.

## 2. Amazon Route 53 (도메인과 로드밸런서 연결)

고객이 브라우저에 서브도메인을 입력했을 때, 정확히 우리 로드밸런서(ALB)로 찾아오도록 이정표를 세웠습니다.

* **레코드 이름:** `wisentm` (결과적으로 `wisentm.ncc-scm.com`이 됨)
* **레코드 유형:** `A` (IPv4 주소 라우팅)
* **별칭(Alias) 설정:** `Yes` ➔ 트래픽 라우팅 대상을 아시아 태평양(서울) 리전의 `was-alb` 로드밸런서로 직결.

## 3. ALB 리스너 및 라우팅 설정 (트래픽 분배)

로드밸런서가 외부의 접속 요청을 받아 내부 도커 컨테이너(타겟 그룹)로 어떻게 넘겨줄지 규칙을 정의했습니다.

* **HTTPS:443 (신규 생성):** * ACM 인증서(`ncc-scm.com`) 장착 완료.
* **액션:** 들어온 트래픽의 암호를 푼 뒤 내부의 `nginx-front-tg2` 타겟 그룹으로 안전하게 전달(Forward).


* **HTTP:80 (규칙 변경):** * **액션:** 보안 강화를 위해 기존 Forward 규칙을 삭제하고, **HTTPS:443으로 강제 이동(Redirect)** 하도록 변경.
* **HTTP:8089 / 8090 (현행 유지):** * 기존 모바일 앱 API 및 소켓 통신(포트 기반 라우팅)의 서비스 연속성을 위해 당분간 유지.

## 4. EC2 보안 그룹 (방화벽 개방 및 트러스트 설정) 

아무리 길을 잘 만들어도 방화벽이 막혀있으면 소용이 없습니다. 외부망과 내부망의 방화벽 역할을 명확히 나누어 설정했습니다.

**① 로드밸런서 방화벽 (`sg-015d11811d175e610` / WiseNTM-ALB-SG)**

* **역할:** 인터넷 망에서 들어오는 불특정 다수의 트래픽을 필터링.
* **추가된 규칙:** * `HTTPS (443)` ➔ 소스: `0.0.0.0/0` (전 세계 어디서든 안전한 암호화 접속 허용)
* `HTTP (80)` ➔ 소스: `0.0.0.0/0` (접속 시 https로 리다이렉트 시켜주기 위해 통로 개방)



**② EC2(WAS/Nginx) 서버 방화벽 (`sg-056b1b5e9516c0004` / EMQX Server SG)**

* **역할:** 로드밸런서를 무사히 통과한 '깨끗한 트래픽'만 내부 서버로 들여보냄.
* **수정된 규칙:** * 프론트엔드 타겟 포트(예: 8093 또는 80)에 대한 인바운드 규칙 생성.
* **소스(Source):** 특정 IP가 아닌, 로드밸런서의 보안 그룹 ID(`sg-015d11811d175e610`)를 지정.
* **효과:** "오직 우리의 ALB를 거쳐서 들어온 손님만 이 포트로 입장할 수 있다"는 강력한 내부망 보호 체계 완성.
